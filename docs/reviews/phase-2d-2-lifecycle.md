# Phase 2d-2 — native lifecycle and real-filesystem adapter review (round 1)

1. **High — `src-tauri/src/watch.rs:577` / `src-tauri/src/watch_check.rs:109`: the native-ready handoff does not deliver reliably, and the mandatory integration gate fails.** `ready` is published immediately after `NativeWatch::start` returns and the baseline finishes, but it does not establish that the native stream can deliver. In a focused run on the review host (`cargo test -p espansoconfig --bin espansoconfig watch_check:: -- --test-threads=1`), 3 of 6 tests failed: the principal test timed out at `watch_check.rs:133` waiting for the first config edit, the successful-reopen test timed out waiting for the live tree's edit, and the failed-reopen test timed out waiting for the retained watcher's edit. All three waited the full 120 seconds and reported zero unrelated observations. The unavailable-root polling test and shutdown test passed, which narrows the failure to the healthy-native path rather than the core rescan path. This leaves both the commissioned real-filesystem evidence and the claimed no-gap native/baseline handoff unproved on the current supported platform. Close this by making native establishment/readiness and the baseline handoff robust against the backend's asynchronous startup (or otherwise removing the missed-write window without making polling the normal steady-state mechanism), then make all six focused lifecycle tests pass repeatedly on the supported macOS target.

2. **High — `src-tauri/src/commands.rs:374`: replacement can deadlock while joining a worker that is inside the injected sink callback.** `open` holds `WorkspaceSession::open`, sends `Stop`, and joins at lines 375–382. The worker invokes the public, unconstrained `ObservationSink` synchronously at `watch.rs:606–610`. A sink that re-enters the session (for example, calls `watch_status`, directly or through a future consumer) can therefore wait for `open` while `open` waits for that callback to return. The decision record's statement at `docs/decisions/2d-2-notes.md:67` that the join is safe because “the worker never takes that lock” overlooks code reached through the sink and is not a guarantee the implementation gives. Close this by ensuring replacement never joins while holding a mutex that a worker callback can acquire—typically with a separate replacement-serialization mechanism and a non-session-locking sink/queue boundary—and add a deterministic test that blocks/re-enters from the sink while replacement occurs and proves cancellation and join complete.

3. **Medium — `src-tauri/src/commands.rs:378`: epoch rollover reuses an epoch and can attribute queued stale observations to a new workspace.** `saturating_add(1)` leaves the epoch at `u64::MAX` on every later successful replacement. That contradicts the monotonic “previous epoch plus one” guarantee in `docs/decisions/2d-2-notes.md:76–82`; once 2d-4 lets observations outlive their watcher, equal epoch values no longer distinguish the replaced and replacement workspaces. The same record also says the old worker is joined before the new epoch exists, while the code computes `next` before `shut_down()`. Close this with checked, non-reusing epoch allocation and a typed terminal policy (or a wider/nonzero generation type), plus a boundary test proving a successful replacement can never reuse an epoch; amend the decision record so its stated ordering matches the code.

4. **Medium — `src-tauri/src/watch_check.rs:189`: the principal test does not exercise creates, atomic renames, edits, and removals under both roots.** It edits `config/default.yml` once, but the create (`:216`), atomic replacement (`:232`), and removal (`:262`) all operate only under `match/`. Thus the test does not provide the requested operation matrix under both `config/` and `match/`, despite the name-position claim at `watch_check.rs:174–176` and the headline claim at `docs/decisions/2d-2-notes.md:12–14`. Close this by exercising and asserting all four real filesystem operation shapes under each root (including exact bytes/revisions and membership classification), preferably as isolated cases so one early timeout does not prevent the rest of the matrix from executing.

5. **Low — `src-tauri/src/watch.rs:114`: the documentation overstates recoverability of discarded production observations.** Lines 117–121 say a dropped observation is not lost forever because the engine tracks the path and “2d-4's first drain starts from the tracked state then current”; the same claim appears at `docs/decisions/2d-2-notes.md:100–112`. In this implementation the engine is private to the worker and exposes no snapshot/drain surface, while the production sink discards the only emitted value. No present code guarantees that a future drain can recover an already discarded observation. Close this by limiting the record to the actual 2d-2 guarantee—observations are deliberately unconsumed—or by deferring and then documenting the concrete bootstrap/rescan mechanism when 2d-4 implements it.

## Round 3

1. **High — `src-tauri/src/watch.rs:621` / `docs/decisions/2d-2-notes.md:114`: one non-returning sink callback blocks the process-global serial reaper, so later callback-initiated teardowns need not be joined and their handles can accumulate without bound.** `hand_to_reaper` has one process-lifetime consumer, and that consumer performs a blocking `JoinHandle::join()` before reading the next `Reap`. If the first torn-down worker never returns from its sink callback, the reaper remains in that join forever. Successor workers can nevertheless be installed and can independently tear themselves down; their `Reap` values then remain queued even after those workers exit, their `joined` flags remain false, and repeated generations can grow the queued handle set without a bound. This does not reintroduce self-join—the thread-id comparison at `watch.rs:672` is correct—but it makes the record's unconditional statement that, “on the reaper, the join completes after that exit” false for a later worker that has exited behind a stuck predecessor. Section 5 item 12 acknowledges that serial joining delays every later reap, but “delays” may mean forever and the claimed loss is not little when it defeats the completion handshake and retains every later handle. Close this with an off-worker teardown design in which one unfinished worker cannot prevent finished workers from being joined, with an explicit bounded policy for permanently unfinished workers/queued handles; add a deterministic test that parks one callback forever (or until cleanup), submits a second callback-initiated teardown whose worker does exit, and proves the second join handshake completes without relying on FIFO release. Rewrite §2.1, §5 item 12, the round-2 closure text, and any “the reaper's join” name-position claims to state only the guarantee the resulting implementation provides.

1. **High — `src-tauri/src/watch.rs:614` / `src-tauri/src/watch.rs:646` / `src-tauri/src/watch_check.rs:863` / `docs/decisions/2d-2-notes.md:44`: the fix closes starvation, but the code and record repeatedly promise chronological “exit-order” joining that the sweep cannot provide.** `reap_forever` retains `Reap`s in hand-over order and, on each sweep, iterates that vector in that same order. `JoinHandle::is_finished()` reports only whether a worker is finished at the instant inspected; it does not report when that worker exited. Thus “joins workers in the order they exit, never in the order they were handed over” is not a guarantee this implementation gives, and the commissioned test cannot prove it: the test proves the narrower and important property that a still-unfinished earlier handoff cannot block a finished later handoff. The false ruling occupies name positions throughout the module docs, reaper docs/comments, test headline/doc comments, §1, §2.1, §5 item 12, and the round-3 closure (§6), despite the record saying the name-position pass was written from what the code now says. Close this either by rewriting every current guarantee and test description to the exact property—each sweep joins every handle it observes finished, without blocking on unfinished handles and irrespective of earlier handoffs—or by adding an actual worker-completion notification/order mechanism if chronological exit order is required. Keep the §6 historical correction convention when amending the newly recorded round-3 closure.

### Verified closure and scope

- The round-3 starvation mechanism itself is closed. A `Reap` is taken into exactly one sweep; an unfinished handle is returned to `pending`, while a finished handle is joined once, its flag is stored only after that join returns, and the value is then released. A stuck handle neither causes a blocking `join` nor prevents later finished handles from being inspected. With pending handles, the timed channel receive wakes for a new handoff or times out after 50 ms; with no pending handle, the reaper blocks on `recv`. Consequently a handoff during a sweep or timed wait is eventually received, a stuck handle plus an empty channel neither spins hot nor sleeps forever, and channel disconnection is handled without losing held handles.
- The bounded retained-state policy is implemented for quiescent input: one held `Reap` per permanently unfinished worker; exited workers are removed on a later sweep. “Within about one interval” is scheduling language, not a hard real-time bound. The implementation uses `recv_timeout` while handles are pending rather than a blind sleep, which preserves the intended cadence and also lets a new handoff wake the reaper early.
- The commissioned test sequences A's handoff before constructing B, waits for B's callback teardown, then requires B's post-join handshake while A is still parked and its probe remains incomplete. That genuinely rejects the old hand-over-order blocking join. Its waits are bounded; normal cleanup releases A and waits for A's handshake, while panic unwinding drops `release_tx`, disconnecting and waking A's bounded receive rather than leaving its thread parked forever. Both fixtures are match-only, so polling is only the test vehicle.
- The round-2 closure text remains intact at `docs/decisions/2d-2-notes.md:609-640`; its round-3 correction is appended at lines 642-649 rather than silently rewriting the historical claim.
- The narrower-instance and scope sweeps found no further cross-worker starvation site: `Drop` performs one intentional in-place join, `menu.rs` waits for one one-shot result, worker inboxes are per-worker, and the test-side `within()` policy abandons its worker.
