# Phase 2c-5 — restore from backup design consult

## VERDICT

Phase 2c-5 should add a read-only backup catalogue in `espansoconfig-core`, expose only opaque catalogue identities and valid UTF-8 backup text across three read commands, model a restore as an immutable preview and a one-shot confirmation in `src/lib/browser/`, and send the confirmed text through the existing `save_raw_document` and `BrowserState.saveRawDocument` path. It should add no seventh writer and no restore-specific save finding. A restore is refused while any write surface for that document is open; a later conflict overwrites neither side and uses the existing adoption protocol. The screen is a third-pane mode that shows the exact candidate through `SourceText`, names the destination, and makes a second, identity-bound confirmation the only producer of a submission. The batch name is an ordering label, not evidence of file history or authenticity. Cut the work into seven dependency-ordered steps: core catalogue, read-only wire, browser values, screen and mounted evidence, temporary instrument, bilingual WKWebView reading, and complete instrument removal.

## Q1 — Command shape

**Ruling: restore is a content path on the sixth writer, `save_raw_document`; add read-only backup commands, not a seventh writing command.**

The existing transaction already has the exact mutation: `SaveContent::ReplaceText` is explicitly the whole-replacement arm and requires a backup session (`crates/espansoconfig-core/src/persist/save.rs:415-458`). `save_one_raw_document` lowers text to that arm, gives it no distinguished match, and passes it through `run_one_save` (`src-tauri/src/commands.rs:1437-1474`); `run_one_save` supplies the session backup and is the shared cache/coherency tail (`src-tauri/src/commands.rs:881-975`). A `restore_backup` writer would either duplicate that policy or become a thin second name for it. Neither buys an invariant. Direct replacement is forbidden because `save_document` owns the lock, locked revision check, candidate gate, backup, and commit (`crates/espansoconfig-core/src/persist/save.rs:1160-1311`), and the repository records that calling a lower writer from the transaction deadlocks because the lock is not reentrant (`CLAUDE.md:427-439`).

The frontend should read one backup entry once, retain the returned UTF-8 string and its `ContentRevision`, render that same value, and pass that same string unchanged to `BrowserState.saveRawDocument`. This is the truthful ordering:

1. the candidate shown is the candidate sent;
2. every finding, including `DocumentDoesNotParse`, is computed from that submitted candidate, whose own hash is in the finding (`crates/espansoconfig-core/src/persist/save.rs:1754-1768`);
3. `baseRevision` is the target document revision captured when the restore value opens, not a revision inferred from the backup name and not a revision refreshed immediately before sending; the locked read then conflicts if the target moved (`src/lib/ipc/commands.ts:632-640`);
4. the person can be told exactly which live document will be wholly replaced and can inspect the exact candidate before confirming.

A dedicated command that accepts only a backup identity would have to read it again after the preview. Unless it also accepted and checked the previewed backup hash, it could write bytes the person never saw; if it accepted the text or hash, it would merely rebuild the ordinary replacement protocol under another name. The backup's hash is evidence that preview and submission agree, never a base revision for the live target.

## Q2 — The core read API

**Ruling: add a non-mutating `BackupCatalog` with opaque batch and entry identities, explicit scan results, byte reading, UTF-8 conversion, target mapping, and one shared newest-first order; it must revalidate every identity at use and never create, rotate, delete, follow a symlink, or treat the ownership marker as authentication.**

The write-side `BackupSession` currently hands Phase 2c only a possibly nonexistent root path (`crates/espansoconfig-core/src/persist/backup.rs:784-829`); `capture` is crate-private and rotation occurs only after a successful first copy (`crates/espansoconfig-core/src/persist/backup.rs:861-938`). The new public read side should be separate from that stateful session:

```text
BackupCatalog::rooted_at(config_root: &Path) -> BackupCatalog
BackupCatalog::scan_batches() -> Result<BackupBatchScan, BackupReadError>
BackupCatalog::scan_entries(batch: &BackupBatchId) -> Result<BackupEntryScan, BackupReadError>
BackupCatalog::entry_for_target(batch: &BackupBatchId, target: &Path)
    -> Result<Option<BackupEntry>, BackupReadError>
BackupCatalog::read_entry(entry: &BackupEntryId) -> Result<BackupBytes, BackupReadError>
BackupBytes::utf8() -> Result<BackupText, BackupReadError>
```

`BackupBatchId` should privately hold the exact directory name plus parsed `stamp` and numeric `counter`; `BackupEntryId` should privately hold that batch identity plus a validated relative component path. `BackupBatch` exposes the opaque id and display name, not an absolute path. `BackupEntry` exposes its opaque id, a `WirePath` display path, byte length, and a target classification such as `InConfigRoot { relative_path } | OutsideConfigRoot`; it does not let the frontend manufacture a filesystem path. `BackupBytes` carries bytes and `ContentRevision::of_bytes`; `BackupText` carries the exact `String` and the same revision. `BackupBatchScan` and `BackupEntryScan` carry eligible values plus counts/codes for unrecognised and unreadable entries, so the UI need not turn an incomplete scan into “no backups.”

There must be one parsed ordering function used by catalogue and rotation: descending `(stamp string, counter number)` for display, with rotation reversing the same order to remove oldest. The current grammar returns exactly those operands and explains why the counter is numeric (`crates/espansoconfig-core/src/persist/backup.rs:1138-1179`), while `rotate` currently repeats the tuple and sorts it ascending (`crates/espansoconfig-core/src/persist/backup.rs:1627-1699`). Do not sort whole names lexicographically and do not parse the stamp into a claimed time.

Enumeration admits only a real directory whose strict name parses and whose real marker file begins with the format identifier. Foreign names, unmarked batch-shaped directories, regular files, and symlinked batch names are skipped, reported, and never counted as eligible—exactly the ownership boundary rotation already applies (`crates/espansoconfig-core/src/persist/backup.rs:1594-1610`, `crates/espansoconfig-core/src/persist/backup.rs:1663-1675`). A missing backup root is an explicit empty/missing scan outcome because the root legitimately may not exist (`crates/espansoconfig-core/src/persist/backup.rs:824-828`); an existing root that is a symlink, not a directory, or not private is a typed refusal, matching the checks already required before writing (`crates/espansoconfig-core/src/persist/backup.rs:1213-1265`).

Entry walking must exclude the marker, reject `.`/`..` and non-normal components, never follow a symlink at any level, and offer only real regular files. Every `scan_entries`, mapping, and read call rechecks the root, batch grammar, real-directory status, marker, containment, and leaf type because rotation or another process may change the tree between calls. A disappeared batch/entry is a typed stale/gone result, not an empty file. The existing path mapping must be made a shared reversible value rather than copied: in-root targets retain their relative path, `_outside` is an escaped second namespace, and non-normal external components are dropped (`crates/espansoconfig-core/src/persist/backup.rs:999-1041`). Restore should offer only entries that map exactly to the selected live `DocumentContext.path`; outside-root entries may be listed for disclosure but are not a licence to invent a document or arbitrary write target. `DocumentContext`, not a wire display path, is the authoritative absolute/relative/kind tuple (`crates/espansoconfig-core/src/model/document.rs:57-74`).

The core byte read is necessary for byte fidelity, but this phase's restore route then requires valid UTF-8. Invalid UTF-8 returns `BackupReadError::NotUtf8 { entry, offset }` and cannot be previewed or sent through the `&str` replacement arm. That matches `document_text`, which returns unchanged valid UTF-8 and refuses at the first invalid byte rather than decoding lossily (`crates/espansoconfig-core/src/workspace/mod.rs:492-505`, `crates/espansoconfig-core/src/workspace/mod.rs:655-665`; `CLAUDE.md:477-482`). It is not acceptable to normalize, replace invalid bytes, or call the result “raw bytes.” Reading never triggers rotation: rotation is destructive, is currently the crate's only recursive deletion, and is deliberately coupled to a successfully written capture (`crates/espansoconfig-core/src/persist/backup.rs:1588-1625`).

Finally, a marker means “recognised as this application's batch format,” not “untampered.” The module says anything able to write the root can forge the marker (`crates/espansoconfig-core/src/persist/backup.rs:62-76`). Treat every entry as untrusted input: validate its path and type, parse it only as a candidate, and let the ordinary save findings judge it. No sentence may say the application verified that it wrote or preserved these bytes.

## Q3 — The wire and the findings

**Ruling: add three read-only wire operations and their typed catalogue/refusal values; add no restore-specific acknowledgeable finding, while retaining every finding the ordinary replacement candidate produces.**

The narrow wire should be `list_backup_batches`, `list_backup_entries`, and `read_backup_text`. The first two return the core scan summaries; the last accepts opaque `BackupEntryId` plus the selected `DocumentId`, re-resolves the latter through the workspace's authoritative `DocumentContext`, verifies the entry maps to that target, and returns `{ entry, document, text, revision }`. A display path is never authority: `DocumentSummary.relative_path` is explicitly display data and the session-local id is what callers hand back (`crates/espansoconfig-core/src/workspace/mod.rs:282-301`). All new errors are codes plus structured operands—missing root, refused root, unrecognised/stale batch, stale entry, path/type refusal, I/O, and `NotUtf8 { offset }`—and cross both dictionaries through typed accessors; components may not construct keys (`CLAUDE.md:493-499`). The core API remains Tauri-free, as required by the architecture boundary (`CLAUDE.md:501-507`).

There is no new `RestoreReplacesDocument` finding. A finding belongs to the candidate gate; “the person chose Restore” is UI authorization, not a property validation can infer from identical text. Adding route provenance to `SaveContent` solely to manufacture that finding would make two semantically identical replacement candidates receive different transaction verdicts and would turn the sixth writer into a hidden seventh protocol. The destructive consent is instead the opaque, one-shot confirmation ruled in Q5. This has the same admitted boundary as deletion: the browser transition can make confirmation the only producer it exposes, but structural TypeScript and a direct IPC import cannot prove that every caller used it (`src/lib/browser/matchDeletion.ts:541-565`). The decision record must say that limitation in the same sentence, not claim the core enforces restore intent.

Existing findings remain mandatory. A parseable backup receives the same projection and validation pass as every replacement (`crates/espansoconfig-core/src/persist/save.rs:1718-1738`). An unparseable backup receives `DocumentDoesNotParse`, bound to the exact candidate revision, and may commit only after exact acknowledgement (`crates/espansoconfig-core/src/persist/save.rs:1700-1709`, `crates/espansoconfig-core/src/persist/save.rs:1781-1788`). That finding is sufficient for the parse-risk claim only; it must not be presented as consent to whole-file replacement. “This backup is older than another state” has no reliable predicate: batches are sessions, the name is a clock-derived directory label, and retention promises neither chronology of the target file nor recoverability (`crates/espansoconfig-core/src/persist/backup.rs:13-41`, `crates/espansoconfig-core/src/persist/backup.rs:1081-1093`). “The file was edited since preview” is not a finding either; it is precisely the locked revision mismatch and existing conflict arm.

Yes, the restore itself backs up the current live file before destroying it. `ReplaceText` refuses a caller with no backup session (`crates/espansoconfig-core/src/persist/save.rs:1142-1154`), and the transaction takes the copy after the verdict but before commit (`crates/espansoconfig-core/src/persist/save.rs:1256-1269`). If capture fails, `take_backup` maps it to `SaveError::Backup`, whose contract says the rename was not reached (`crates/espansoconfig-core/src/persist/save.rs:747-775`, `crates/espansoconfig-core/src/persist/save.rs:1360-1385`); if this session already captured the target, `backup: None` on success is legal because that session's pristine copy already exists (`crates/espansoconfig-core/src/persist/save.rs:654-676`). The screen may therefore say a failed pre-commit backup stopped this attempt only when that typed arm is present; it may not promise a newly created backup on every successful restore.

## Q4 — The frontend model

**Ruling: add one restore model in `src/lib/browser/`, submit only through `BrowserState.saveRawDocument`, refuse a restore while any write surface for the target is open, and otherwise use the existing sealed invalidation and conflict-adoption protocols unchanged.**

The model should own catalogue loading, exact selected `BackupText`, selected target, target `baseRevision`, candidate hash, preview generation, pending confirmation, acknowledgement, in-flight state, and the three ordinary save outcomes. Changing the batch, entry, target, candidate, or observed target revision withdraws confirmation and acknowledgement. Only a confirmed immutable submission may invoke `BrowserState.saveRawDocument(document, baseRevision, text, acknowledgement)`. That wrapper is the one production place that couples the command result to cache invalidation, remembers a conflict without installing it, and seals the whole-document answer (`src/lib/browser/workspace.svelte.ts:2575-2659`). The restore model must then call `openWholeDocumentSave(sealed, forget)` and handle `invalidation` and `issuerInvalidation` beside—not instead of—the committed outcome. The seal calls `forget` only for `saved && committed`, before releasing the result, and a throwing callback is returned as a separate failure (`src/lib/browser/invalidation.ts:312-370`).

Do not reuse `documentHasUnsavedDraft` as though it answered the full question. It measures any open match editor, dirty or pristine, explicitly excludes the raw draft, and cannot prove its caller supplied every editor (`src/lib/browser/matchDuplication.ts:300-339`). Add a coordinator-owned `OpenWriteSurface` value covering match editor, creator with a chosen target, deleter, mover, duplicator, raw editor, and restore itself. Starting and confirming restore are refused when another surface names the target. The localized sentence says that a write surface for this file is open and must be closed; for a match editor it may add that this application cannot tell whether it was edited. It must not say “unsaved changes.” Over-refusal is correct here: warning and then invalidating would strand an opaque operation or draft; silently closing would discard it.

The refusal is an affordance, not the post-commit safety proof. A surface can open after preview, so confirmation rechecks the coordinator immediately before producing the submission. If a commit nevertheless occurs, the synchronous whole-document invalidation closes/marks terminal every surface for that document, drops every projection and selection identity, and never tries to carry a `MatchId` across the new revision. A committed replacement permanently has `moved: null` (`src/lib/browser/invalidation.ts:111-145`). If invalidation fails, the restore remains reported as committed and the screen separately says the window is out of step; a failure after commit never unwrites the file (`src/lib/browser/invalidation.ts:53-65`).

Restore participates in the current conflict protocol without exception. A conflict writes nothing, stays separate from the retained candidate, and is installed only through `adoptDiskVersion`, whose answer type is exactly `installed | alreadyThere | refused` (`src/lib/browser/saveOutcome.ts:1375-1381`) under origin, spend, document, and projection-generation guards (`src/lib/browser/workspace.svelte.ts:600-669`). There is no *retry restore anyway*. After confirmed adoption, the old restore confirmation is spent; the person must review the still-retained candidate against the newly installed target and issue a fresh restore confirmation with `diskRevision` as the new expected revision. The original expected revision is the target revision captured when this restore preview opened. It is never the backup candidate revision, batch stamp, or whatever revision the browser happens to project just before send.

## Q5 — The screen

**Ruling: restore is a third-pane mode reached from the document's whole-text surface; it shows the selected backup text before submission and uses a preview step plus a one-shot confirmation bound to the exact target, base revision, backup entry, and candidate hash.**

The raw viewer already establishes that whole-file text belongs in the third pane and is reachable even when parsing failed (`src/lib/components/DetailPane.svelte:133-149`); it renders a real whole document with `<SourceText text={view.text} documentStart />` (`src/lib/components/DetailPane.svelte:543-556`). Restore should reuse that primitive, including named control characters and horizontal scrolling, never a `<textarea>`: input controls normalize carriage returns, while `SourceText` is the established read-only representation (`CLAUDE.md:361-369`, `CLAUDE.md:467-475`). The screen should show the destination relative path, recognised batch-name label, candidate byte/character facts that are actually measured, exact candidate text, and a direct warning that confirming replaces the whole destination file. Showing the target's currently held text as a second stacked `SourceText` is useful only if labelled as the window's loaded observation; it must not be called current disk state. A diff is unnecessary and must not become writable.

Use three states, not a modal detached from its evidence: select a recognised batch/entry; inspect the candidate; press *Prepare to replace file*, which produces an opaque pending confirmation; then press a visually distinct *Replace entire file with the shown text*. The confirmation is at least as strong as deletion's two-phase value, where the request records the exact identity and only `confirmDelete` can produce a submission (`src/lib/browser/matchDeletion.ts:493-512`, `src/lib/browser/matchDeletion.ts:541-605`). Here the pending value binds `DocumentId`, target `baseRevision`, `BackupEntryId`, candidate `ContentRevision`, and preview generation; confirmation rechecks all five plus the open-surface predicate. It is one-shot and is withdrawn on navigation, selection change, catalogue refresh, conflict, refusal acknowledgement change, or any candidate change. Requiring the person to type a filename adds ritual but no stronger binding, so do not add it.

The batch label is not a timestamp assertion. `batch_stamp` formats the process clock to obtain a sortable directory name and explicitly calls it a directory name rather than a measurement (`crates/espansoconfig-core/src/persist/backup.rs:1081-1093`). The UI may say *Backup batch named 2026-…* and may order recognised batches newest-name-first. It may not say *taken at*, *the file at*, *version from*, or convert the name into a localized historical time. The counter disambiguates sessions created under the same label; it is not an edit sequence.

## Q6 — What restore must never claim

**Ruling: every sentence must be limited to the candidate bytes, selected destination, recognition checks, and observed save outcome; restore is neither undo nor proof of history, authenticity, recoverability, validity, or espanso behavior.**

Forbidden screen, dictionary, comment, test, and decision-record claims include:

- **Undo**, **Undo last change**, or **Revert the last edit**. A batch is a session, may contain the first pre-save image of several files, and retention is ten sessions rather than an operation history (`crates/espansoconfig-core/src/persist/backup.rs:13-41`).
- **Back to how it was**, **original version**, **previous version**, or **exact state of the configuration**. The candidate is one file's copied bytes, not workspace state; backups deliberately omit ACLs even though they preserve file bytes, mode, and extended attributes (`crates/espansoconfig-core/src/persist/backup.rs:84-110`).
- **The version from `<time>`**, **taken at `<time>`**, **newest backup**, or **older/newer file version**. Only newest-by-name is proved, using a process-clock label and numeric collision counter (`crates/espansoconfig-core/src/persist/backup.rs:1081-1093`, `crates/espansoconfig-core/src/persist/backup.rs:1147-1178`).
- **Created by this application**, **verified backup**, **authentic**, **untampered**, or **safe backup**. The marker is deliberately forgeable and protects only against accidental ownership confusion (`crates/espansoconfig-core/src/persist/backup.rs:62-76`). The truthful term is **recognised backup batch**.
- **Recoverable**, **always available**, **kept forever**, or **a new backup was made**. Rotation retains ten sessions and `BackupRecord` itself is not a recoverability promise; `backup: None` is legal on success (`crates/espansoconfig-core/src/persist/backup.rs:119-125`; `crates/espansoconfig-core/src/persist/save.rs:594-608`).
- **Valid**, **invalid**, **works with espanso**, **will restore your snippets**, or any statement about which definition wins. A parse finding claims only that this parser did not parse the exact candidate, and D2u forbids inferred scalar semantics (`crates/espansoconfig-core/src/persist/save.rs:1700-1714`; `CLAUDE.md:517-522`).
- **Keep my draft**, **merge**, **apply backup changes**, or **restore selected snippets**. The operation is an unmerged whole-document replacement and every identity in the destination becomes stale (`src/lib/browser/invalidation.ts:1-18`).
- **Nothing was changed** for a conflict/refusal without the narrower predicate *this restore attempt wrote nothing*; another writer may have changed the disk, and the conflict payload distinguishes the locked `found` observation from the later `diskRevision` observation (`src-tauri/src/commands.rs:1476-1486`).
- **Restore failed** after a committed write whose invalidation/reprojection failed. The bytes committed; only the window failed to return to step (`src/lib/browser/workspace.svelte.ts:2618-2635`).
- **Unsaved edits are open** when the predicate sees only an open match editor. The repository explicitly records that the coordinator cannot observe its derived dirty state (`src/lib/browser/matchDuplication.ts:310-325`).

Positive copy should be correspondingly narrow: *Replace this file with the text shown from the selected recognised backup entry*; *This restore attempt wrote the file*; *The file was written, but this window could not reload it*; and *The file changed after this restore preview was prepared, so nothing was overwritten by this attempt.* Every code is rendered through a typed i18n accessor in English and Spanish (`CLAUDE.md:493-499`).

## Q7 — The split

**Ruling: use seven steps, cut exactly by failure mode and dependency order; only step 6 owes a WKWebView reading, while step 4 supplies the phase's mounted evidence and step 5 rebuilds the disposable instrument.**

1. **2c-5-1 — core backup catalogue, with no caller.** Add the types, shared batch parser/order, root and marker recognition, recursive non-following entry scan, reversible target mapping, exact byte read, UTF-8 refusal, and typed read errors. Keep every operation read-only. Rust tests owe missing/refused roots, stamp/counter order, foreign/unmarked/symlinked batches, symlinks at every entry depth, marker exclusion, non-UTF-8 offset, disappearing entries, outside namespace escaping, target mapping, and proof that enumeration/read never creates or rotates. This step owes model tests; no mounted test and no window reading.
2. **2c-5-2 — read-only Tauri wire.** Add the three commands, opaque serialized ids, dictionary-contract coverage, `DocumentId`-to-context mapping, and TypeScript exhaustive types/fixtures. Prove a forged id/path, wrong target, stale batch, unreadable entry, and invalid UTF-8 are typed refusals, and prove no command calls a writer. This step owes Rust/IPC and TypeScript model tests; no mounted test and no window reading.
3. **2c-5-3 — restore as browser values, nothing drawn.** Add catalogue/preview state, exact candidate retention, open-surface refusal, one-shot confirmation, acknowledgement invalidation, conflict retention, and composition through `BrowserState.saveRawDocument` plus `openWholeDocumentSave`. Model/workspace tests owe every binding change, dirty-unknown wording predicate, all six competing surface kinds, `committed: false`, refusal/acknowledgement, conflict/adopt `installed | alreadyThere | refused`, a second conflict, send uncertainty, committed invalidation failure, and proof that no save is issued without confirmation. No component changes means no mounted test and no window reading; this follows the project's established value-before-choice cut (`CLAUDE.md:221-229`).
4. **2c-5-4 — third-pane screen, i18n, and mounted evidence.** Add the mode, catalogue states, candidate and optional loaded-target `SourceText`, two-stage controls, typed English/Spanish accessors, save outcomes, and accessible focus/scroll behavior. Every changed component gets a mounted interaction test. The mounted matrix proves exact identity-bound confirmation, withdrawal on every change, open-surface refusal, no direct IPC call, parse finding acknowledgement, conflict preservation, committed result wording, and no forbidden historical/authenticity claim. This step owes the mounted-component evidence for the phase but no window reading: a mounted handler test is not a screen (`CLAUDE.md:484-491`).
5. **2c-5-5 — rebuild and review the temporary window instrument.** Reconstruct the probe hooks, deterministic fixtures, driver, fresh bundle-path launch, language selection, external target/backup mutations, and whole-tree byte oracle from the surviving prose. Prove the driver reaches every planned state before using it as evidence. This is a full step because the previous phase deliberately removed the harness and records that the next one must rebuild from prose (`docs/decisions/2c-4c-6-notes.md:96-106`). It owes instrument tests/review, not a product window reading.
6. **2c-5-6 — bilingual WKWebView reading.** This is the only step that owes the window reading. In separate short launches, read English and Spanish for missing root, recognised/unrecognised batches, valid and non-UTF-8 entries, BOM/CRLF/control-character preview, open-surface refusal, confirmation withdrawal, parse-finding acknowledgement, target changed after preview, all three adoption answers where reachable, committed restore, `committed: false`, and committed-but-reprojection-failed. Byte-compare the restored file to the preview fixture and the pre-restore backup to the exact displaced bytes; verify unrelated files and bytes are unchanged. Test keyboard, focus, scroll, viewport reachability, and hit testing. Any component fix in this step invalidates and retakes the affected reading; WKWebView evidence must be short, fresh-bundle launches with language chosen explicitly (`CLAUDE.md:453-465`).
7. **2c-5-7 — remove the instrument and restore production baselines.** Delete both probe sides, hooks, scratch bundles, fixtures, plans, and manifests; sweep for residue; then re-derive all harness-free gate counts rather than copying instrumented figures. It adds no model, mounted, or window evidence. This removal is part of the phase because an instrument must not become production code; the previous consult uses the same separate removal cut (`docs/reviews/phase-2c-4c-design.md:80-84`).

The phase as a whole therefore owes all three required evidence kinds without pretending they are interchangeable: model evidence in steps 1–3, mounted evidence in step 4, and the real bilingual screen reading in step 6. Steps 1–5 and 7 explicitly owe no window reading.

## Q8 — The sharpest failure mode

**Ruling: the sharpest mistake is allowing the selected backup, shown candidate, confirmed candidate, target document, and expected target revision to drift apart; the implementer should read the single instruction below before writing a line.**

> The only restore submission is the exact UTF-8 text whose candidate hash, opaque backup-entry identity, target `DocumentId`, target base revision, and preview generation are bound into one unspent confirmation; send that text unchanged through `BrowserState.saveRawDocument`, and treat every mismatch as “write nothing.”

This is sharper than accidentally bypassing a cosmetic screen state: a preview of entry A followed by a write of entry B, a confirmation carried to another document, or a base revision refreshed at send time can destroy the wrong bytes while every lower-level write primitive behaves correctly. The code already explains why the base revision is the only barrier against overwriting a later disk change (`src/lib/ipc/commands.ts:635-638`), why a confirmation whose values were minted together observes nothing about the live world (`src/lib/browser/matchDeletion.ts:551-565`), and why a committed replacement invalidates every identity before its result can be read (`src/lib/browser/invalidation.ts:312-330`). Those three lessons must meet in one value.

I do **not** agree that the sharpest failure in this phase is prose. The most likely review finding may still be a sentence such as *version from Tuesday*, *undo*, or *unsaved changes*—the repository calls unsupported guarantee claims its worst recurring defect class (`CLAUDE.md:357-359`, `CLAUDE.md:423-425`). But this phase is classified as destructive (`docs/decisions/2c-split-notes.md:126-137`), and its highest-consequence plausible error is behavioral: spending correct consent on different bytes or a different target. Review the binding first, then audit every English, Spanish, JSDoc, test, and decision-record sentence against the exact predicate. Green tests cannot make a false historical or safety claim true, but perfect prose cannot recover a file replaced under mismatched authorization.
